- **`experiment_run.get_run_leaderboard`: run leaderboard declared on an experiment-run reference, paginated; the analytics-path GET deprecated (additive, contract only).** `GET /api/v1/projects/{project_id}/experiment-runs/{experiment_run_ref}/leaderboard` (operation id `experiment_run.get_run_leaderboard`) takes the server-issued reference `^experiment_run_[0-9a-f]{32}$` and the explicit project. Query: `limit` (default 20, maximum 100; this replaces the backend's historical default 50 and maximum 200 of the query), `cursor` (opaque sealed string, at most 512 base64url characters, bound to caller, project, run and query) and the backend's own `objective` (`weighted` default, `quality`, `cost`, `latency`), `weights` and `constraints` (JSON-object strings, at most 50 keys, bounded here to 8192 characters) and `request_count` (1 to 1000000, default 1); every other parameter, including retired `page` and `offset`, is the closed 400. The 200 is the new `analytics/experiment_run_leaderboard_response_schema.json`: `data` carries `run_id` (the experiment_run_ref), `ranking_basis` (`objective`, `weights`, `constraints`), `items`, `warnings` and `pagination` (`limit`, `next_cursor` nullable, `has_more` true if and only if `next_cursor` is non-null, required integer `total`), mirroring the backend leaderboard computation. Each item has `rank`, `trial_ref`, `composite_score`, `measures`, `confidence`, `risk_flags` and `recommendation`. The ranking is computed over the full eligible population and only then paginated: non-disqualified first, descending composite score, ranks assigned after that order, so `rank` is unique across pages. The cap of 10000 counts ALL the run's scoped configuration rows before any metric processing (above it the closed 503). The cursor also seals the `analysis_revision` (a per-run monotonic counter bumped in the same transaction as any ranking-relevant configuration or metric write, read from the same snapshot as the ranked rows); a stale or foreign cursor is the closed 400 `invalid_cursor`, echoing nothing. Measure values and scores are any finite JSON number; `warnings` are the builder's four forms and `risk_flags` its four tags. The 1 MiB limit is enforced on the serialized envelope (closed 503); the schema gives no static byte bound. Canonical projection omits config_id: internal configuration-run id (replaced by the shared persisted `trial_ref`, `^(trial_[0-9a-f]{16}|configuration_run_[0-9a-f]{32})$` (both issued formats), via `experiment_run_trial_ref_schema.json`; a run with any unissued reference is the closed 503). Canonical projection omits label: the builder falls back to `Trial <config_id>`, which embeds the internal id. `data.run_id` is the experiment_run_ref. Errors are the closed problems of `analytics/leaderboard_problem_schema.json`. `GET /api/v1/analytics/runs/{run_id}/leaderboard` stays declared, marked `deprecated` and naming the successor; its project beta mount `/api/v1beta/projects/{project_id}/analytics/runs/{run_id}/leaderboard` retires with it. `run_leaderboard_schema.json` and `run_leaderboard_response_schema.json` are unchanged. Removal follows the backend retirement PR after the client receipt. One name policy `^[^\x00-\x1f\x7f]{1,128}$` for every measure name wherever echoed (a query key outside it is the closed 400, a stored metric name outside it the closed 503 for the run); each weight is a number in [0, 1000] (a negative or larger weight is the closed 400, replacing the builder's silent exclusion of negative weights) and the composite is computed over weights normalized to sum to 1, so it is finite. At least one weight must be greater than 0 when weights is given (all-zero, e.g. `{"accuracy": 0}`, is the closed 400 with no echo; omitting weights keeps the default objective path). Each measure's min-max normalization is computed without overflow (values scaled by the largest absolute finite value before subtracting, or an equivalent exact method), so equal values score equal; the composite is a convex combination of normalized terms in [0, 1]. The ranking sorts by the unrounded binary64 composite; equal composites are ordered by the raw values of the weighted measures in descending weight order, ties between equal weights broken by measure name ascending (lexicographic), each compared in that measure's better direction, with a missing raw value ordered after any present value at that step; any remaining tie is broken by ascending trial_ref (lexicographic). The positive-weight rule applies only to a weights map supplied in the request; the response's effective `ranking_basis.weights` may be empty. The response description names both issued `trial_ref` formats.
